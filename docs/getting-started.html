Instalação

Instale o CLI globalmente e crie um projeto — ele já vem apontando para os pacotes @mimir-js/* (npm público, sem token): 

npm install -g @mimir-js/cli
mimir create my-agent
cd my-agent
npm install
npm start                 # roda o assistente de exemplo

Requer Node 18+ (recomendado 20+) e um modelo local (ex.: Ollama) — ajuste o provider em src/providers/.

Estrutura do projeto

O mimir create gera um projeto por convenção — você escreve agentes, tools, providers e workflows: 

src/
  agents/
    assistant/
      assistant.agent.ts   # só a lógica
      assistant.agent.md    # só o prompt
  tools/         # suas tools
  providers/     # seus providers
  workflows/     # seus workflows
  config.ts      # log / report
  main.ts        # ponto de entrada

Criando um agente

Gere o esqueleto com a CLI:

mimir g agent explorer

Isso cria src/agents/explorer/explorer.agent.ts e o explorer.agent.md irmão. Um agente é uma classe decorada com @Agent — a lógica no .ts:

src/agents/explorer/explorer.agent.ts
import { Agent } from "@mimir-js/core";
import { ShellTool } from "@mimir-js/tools";
import { LocalOllamaProvider } from "../../providers/ollama.provider.js";

@Agent({
  provider: LocalOllamaProvider,
  tools: [ShellTool],
  prompt: "./explorer.agent.md",
})
export class ExplorerAgent {}
  • provider — uma classe (instanciada com new) ou uma instância já configurada.
  • tools — classes @Tool (ou objetos ToolType) injetadas no agente.
  • prompt — obrigatório: caminho do markdown (relativo ao arquivo do agente).
A classe representa só a lógica. No fluxo padrão você nem precisa de corpo — o framework monta o pipeline, chama o provider e injeta as tools. Para lógica própria, use os hooks ou um método run(input, ctx).

Prompt (markdown)

O prompt fica fora do TypeScript, no .agent.md. Assim você versiona e edita o comportamento do agente sem tocar no código:

src/agents/explorer/explorer.agent.md
# Agente explorer

Você é o agente **explorer**, especialista em explorar o sistema de arquivos.
Use a tool `shell` para inspecionar diretórios e responda de forma objetiva.

Formas de referenciar o prompt no @Agent:

promptResolução
"./explorer.agent.md"relativo à pasta do arquivo do agente
"/abs/caminho/x.md"caminho absoluto
new URL("./x.md", import.meta.url)via import.meta — sem "mágica"

Tools

Uma tool é uma classe decorada com @Tool({ name, description, schema }); a lógica fica em execute(input). O schema (Zod) valida os argumentos.

src/tools/read-file.tool.ts
import { Tool } from "@mimir-js/core";
import { readFile } from "node:fs/promises";
import { z } from "zod";

@Tool({
  name: "read_file",
  description: "Lê o conteúdo de um arquivo.",
  schema: z.object({ path: z.string() }),
})
export class ReadFileTool {
  async execute({ path }: { path: string }) {
    return readFile(path, "utf8");
  }
}

Uma tool chamando um workflow

O construtor da tool pode receber o WorkflowRuntime injetado (DI), para disparar outro workflow: 

import { Tool, WorkflowRuntime } from "@mimir-js/core";
import { z } from "zod";
import { DeployWorkflow } from "../workflows/deploy.workflow.js";

@Tool({
  name: "deploy",
  description: "Executa o workflow de deploy.",
  schema: z.object({ repository: z.string() }),
})
export class DeployTool {
  constructor(private readonly runtime: WorkflowRuntime) {}

  async execute(input: { repository: string }) {
    return this.runtime.run(DeployWorkflow, { input });
  }
}

Providers

Um provider conversa com o modelo. O padrão é criar uma subclasse com as credenciais já configuradas, em src/providers/: 

import { OllamaProvider } from "@mimir-js/core";

export class LocalOllamaProvider extends OllamaProvider {
  constructor() {
    super({ host: "http://localhost:11434", model: "qwen2.5-coder:7b" });
  }
}

Também há o OpenAIProvider ({ apiKey, model }). O agente referencia a classe do provider — sem hardcode de credenciais.

Workflows

Um workflow orquestra vários agentes num único pipeline, compartilhando o estado. Os passos ficam em steps e podem ser combinados e aninhados:

  • agente (a classe) → passo sequencial; a saída de um alimenta o próximo;
  • parallel([...]) → passos concorrentes sobre o mesmo contexto;
  • loop({ steps, until, maxIterations }) → repete até until(ctx) ou o limite.
src/workflows/explorer.workflow.ts
import { Workflow, parallel, loop } from "@mimir-js/core";
import { PlannerAgent } from "../agents/planner/planner.agent.js";
import { ExplorerAgent } from "../agents/explorer/explorer.agent.js";
import { ReviewerAgent } from "../agents/reviewer/reviewer.agent.js";

@Workflow({
  steps: [
    PlannerAgent,
    loop({
      maxIterations: 5,
      until: (ctx) => ctx.reviewApproved,
      steps: [ parallel([ExplorerAgent, ReviewerAgent]) ],
    }),
  ],
})
export class ExplorerWorkflow {}
A condição do loop lê campos que os agentes gravam no contexto (ex.: ctx.reviewApproved). Para isso um agente precisa de lógica própria (um run(input, ctx) que faça ctx.reviewApproved = ...). Sem isso, o loop roda até maxIterations.

Bootstrap & run

O ponto de entrada fica em src/main.ts:

src/main.ts
import { bootstrapWorkflow } from "@mimir-js/core";
import { ExplorerWorkflow } from "./workflows/explorer.workflow.js";
import { config } from "./config.js";

const app = await bootstrapWorkflow(ExplorerWorkflow, config);

await app.run({
  input: { message: "Olá" },
  memory: { userId: "123", sessionId: "abc" },
});

Rode com npm start. Pontos importantes:

  • input.message é a entrada inicial do pipeline.
  • memory é o contexto inicial/persistente, semeado no estado antes da execução.
  • Para obter o resultado no código (testes, scripts), use runWorkflow(WorkflowClass, input, memory?) ou run(AgentClass, input).

Agent Hooks

A classe do agente pode declarar hooks opcionais (ciclo de vida) para interceptar e manipular o fluxo. Nada é obrigatório — o runtime chama só o que existir.

HookQuandoContrato
beforePrompt(prompt, ctx)antes de enviar ao modeloretorna o prompt (transforma)
beforeTool(call, ctx)antes de executar a tooltroca os args, ou throw cancela
afterTool(result, ctx)após a toolretorno substitui o output
afterResponse(response, ctx)na resposta do passoretorna a resposta (transforma)
onError(error, ctx)em erro no fluxoretorno vira fallback

Contrato dos transformadores: retornou valor → substitui; retornou undefined → mantém.

explorer.agent.ts (com hooks)
import { Agent } from "@mimir-js/core";
import type { AgentHooks, ToolCall, ToolResult } from "@mimir-js/core";

@Agent({ provider: LocalOllamaProvider, tools: [ShellTool], prompt: "./explorer.agent.md" })
export class ExplorerAgent implements AgentHooks {
  // injeta contexto dinâmico no prompt
  async beforePrompt(prompt: string) {
    return `${prompt}\n\n[data] ${new Date().toISOString().slice(0, 10)}`;
  }

  // bloqueia comandos perigosos (throw → cai no onError)
  async beforeTool(call: ToolCall) {
    if (call.name === "shell") {
      const { command } = call.args as { command: string };
      if (/\brm\b|sudo/.test(command)) throw new Error(`bloqueado: ${command}`);
    }
  }

  // corta saída gigante
  async afterTool(result: ToolResult) {
    if (result.output.length > 2000) return result.output.slice(0, 2000) + "…";
  }

  async onError(error: Error) {
    return "Não consegui completar agora."; // fallback
  }
}
Escape hatch: se a classe define run(input, ctx), ela assume o controle total do passo e os hooks automáticos não são chamados. Use run para orquestrar você mesmo (várias chamadas ao provider, loop de tool-use, etc.).

Config & Report

O bootstrapWorkflow aceita um config. Com report: true, ao final da run é gerado um report estilo Playwright (HTML + JSON) em report/: a árvore da execução (workflow → loop / parallel → agent → chat → tool), durações, status e o conteúdo de cada passo.

src/config.ts
import type { MimirConfig } from "@mimir-js/core";

export const config: MimirConfig = {
  report: true, // ou { dir: "report", format: "html" | "json" | "both" }
};

Rode npm start e abra report/index.html (HTML autocontido, sem dependências). É opt-in: sem report, nada é gerado e não há overhead. Não há serviço/telemetria externa.

Logs ao vivo

Para ver o que está sendo executado em tempo real (agentes, chats, tools), use log. É independente do report:

logO que faz
trueárvore indentada no console, com duração por passo
"verbose"idem, incluindo conteúdo (resposta, I/O das tools)
(event) => voidsink customizado (pino/winston, arquivo, JSON lines)
src/config.ts
export const config: MimirConfig = {
  log: true,       // ou "verbose", ou (event) => logger.info(event)
  report: true,
};
saída ao vivo (log: true)
[mimir] ▸ workflow ExplorerWorkflow
[mimir]   ▸ agent PlannerAgent
[mimir]     ▸ chat
[mimir]     ◂ chat  1.01s ✓
[mimir]   ◂ agent PlannerAgent  1.01s ✓
[mimir]   ▸ loop
[mimir]     ▸ parallel
[mimir]       ▸ agent ExplorerAgent
[mimir]       ▸ agent ReviewerAgent   # começam juntos (parallel)
[mimir]         ...
Log é o que acontece agora (streaming); report é o artefato final para analisar depois. Ambos reutilizam a mesma camada de interceptação — uma instrumentação, dois "outputs". Sem log, zero overhead.

Boas práticas

  • Um agente, uma responsabilidade. Prefira agentes focados (planner, explorer, reviewer) orquestrados por um workflow, a um agente "faz-tudo".
  • Prompt no .md, lógica no .ts. Versione os prompts como texto; evite prompts hardcoded em strings.
  • Guardrails com beforeTool. Valide/bloqueie ações sensíveis antes de executar; um throw cai no onError.
  • Sempre um onError. Devolva um fallback para o agente degradar com elegância em vez de quebrar a run.
  • Schemas Zod estritos. O schema da tool é a fronteira de confiança entre o modelo e o seu código.
  • Providers sem credenciais no agente. Configure host/model/apiKey numa subclasse em src/providers/.
  • Loops precisam de condição real. Um agente deve gravar o flag lido pelo until (ex.: ctx.reviewApproved); use maxIterations como rede de segurança.
  • Report só quando precisar. Ligue report: true em dev/CI para depurar; deixe desligado em produção (é opt-in, zero overhead).

Casos de uso

1 · Code review automatizado

Um workflow que planeja, explora o código em paralelo e revisa, repetindo até aprovar — o exemplo ExplorerWorkflow acima: Planner → loop( parallel(Explorer, Reviewer) ).

2 · Agente explorador de arquivos

Um @Agent com ShellTool + ReadFileTool que inspeciona o projeto e responde perguntas — o modelo decide qual tool chamar e o Mimir executa e devolve o resultado.

3 · Ferramenta que dispara um deploy

Uma @Tool recebe o WorkflowRuntime por DI e chama um DeployWorkflow inteiro (workflows aninhados) — útil para orquestrações onde uma decisão do agente inicia outro processo.
